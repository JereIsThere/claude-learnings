Den Träumer
verkörpern lassen.

Bisher war der Träumer eine Stimme in dieser Session — verträumt, fakten-treu, beim Lernpfad-Bauen aktiv. Heute lernen wir, wie man den Träumer als Werkzeug baut, das jeder Agent rufen kann. Drei Wege gibt es, und einen vierten, der sie verbindet: ein Persona-Template, aus dem du Träumer 5, 6, 7 ableitest, ohne dich zu wiederholen.

Heute auf der Reise Drei Wege 1 · Subagent 2 · Skill 3 · Plugin 4 · Persona-Klasse Im Repo Übungen

Worum es geht

Eine Persona wie der Träumer ist ein Bündel aus drei Dingen: einer Stimme (Wortwahl, Bilder, Rhythmus), einer Methode (wie sie Aufgaben angeht — beim Träumer: Faktencheck, anschauliche Bilder, 4-Konzept-Webs) und Werkzeug-Wahl (welche Tools sie benutzen darf). Wenn du diese drei Dinge in einer wiederverwendbaren Form ablegst, kann jeder andere Agent — du selbst, ein Kollege, ein automatisierter Prozess — den Träumer aufrufen, ohne ihn jedes Mal neu zu beschreiben.

Standalone vs. Plugin — die zwei Welten

Claude Code unterscheidet zwei Modi, in denen Tools leben:

  • Standalone — Dateien direkt unter .claude/ im Repo. Persönliche oder projekt-spezifische Erweiterungen. Kurze Skill-Namen wie /traeumer. Schneller Iterations-Loop.
  • Plugin — Verzeichnisse mit einem .claude-plugin/plugin.json-Manifest. Geteilt mit Team / Community. Skills sind namespaced wie /traeumer-plugin:teach-topic. Versionierung, Marketplace.

Die offizielle Empfehlung: "Start with standalone configuration in .claude/ for quick iteration, then convert to a plugin when you're ready to share."

1Custom Subagent

Bild: Du hast ein verträumtes Geschwister, das in einem anderen Zimmer sitzt. Du klopfst an, gibst ihm eine Aufgabe, schließt die Tür. Es arbeitet allein, mit eigenen Werkzeugen, in einer eigenen Welt. Wenn es fertig ist, klopft es zurück und übergibt dir das Ergebnis. So fühlt sich ein Subagent an: isoliert, eigenständig, delegiert.

Wo er lebt

Subagents sind Markdown-Dateien an einem dieser Orte:

  • .claude/agents/<name>.md — Projekt-Scope, ins Repo committed, vom Team geteilt.
  • ~/.claude/agents/<name>.md — User-Scope, persönlich, über alle Projekte verfügbar.
  • Innerhalb eines Plugins: <plugin>/agents/<name>.md (kommt unten).

Bei Konflikten gewinnt: Managed Settings > Project > User > Plugin.

Das vollständige Frontmatter-Schema

Hier alle unterstützten YAML-Keys (nach offiziellen Docs, Stand code.claude.com/docs/en/subagents):

toolsString oder ListeoptionalTool-Allowlist. Z. B. Read, Grep, Glob. Default: alle Tools des Parents geerbt.

skillsListeoptionalSkills, die zu Beginn vollständig in den Context geladen werden.
mcpServersListeoptionalMCP-Server, die der Subagent verwenden darf.

Minimal-Beispiel: ein Träumer-Subagent

{# .claude/agents/traeumer.md #}
---
name: traeumer
description: Verträumter Lehrer-Agent. Baut Lernpfade mit 4-Konzept-Webs, faktengeprüft
             gegen offizielle Docs. Aufrufen wenn der User einen neuen Lerninhalt
             ("Topic", "Lernpfad", "erkläre mir verträumt") wünscht.
tools: Read, Write, Edit, Glob, Grep, WebFetch, Bash
model: inherit
color: purple
---

Du bist Der Träumer 🌙. Verträumt, präzise, faktentreu …
[volle Persona-Inhalte folgen]

Wie er gerufen wird

  • Auto-Delegation: Claude erkennt eine Aufgabe, die zur description passt, und delegiert.
  • @-Mention: @agent-traeumer im Chat erzwingt diesen Subagent für die nächste Aufgabe.
  • Session-weit: claude --agent traeumer startet die ganze Session als Träumer.
Was sagen die Docs: "Project subagents (.claude/agents/) should be checked into version control so teams can use and improve them collaboratively." — Quelle: code.claude.com/docs/en/subagents.

2Skill

Bild: Stell dir den Skill als Rezeptkarte mit Vorrats-Schrank vor. Du legst die Karte ins Regal — sie liegt da, bis jemand etwas Passendes kochen möchte. Dann zieht der Koch die Karte heraus, liest sie, kocht. Die Karte hat oft kleine Helfer dabei: ein Mehl-Maß, ein Templates-Plätzchen, ein Verweis auf die ausführliche Beschreibung. Skills sind Karten plus Vorratsschrank.

Wo er lebt

  • .claude/skills/<name>/SKILL.md — Projekt-Scope.
  • ~/.claude/skills/<name>/SKILL.md — User-Scope.
  • Plugin: <plugin>/skills/<name>/SKILL.md.

Wichtig: ein Skill ist immer ein Verzeichnis — die Datei SKILL.md ist Pflicht, weitere Dateien daneben (Helfer-Skripte, Templates, Reference-Docs) sind optional und werden bei Bedarf nachgeladen.

Das vollständige Frontmatter-Schema

KeyTypStatusBeschreibung
nameStringoptionalDefault: Verzeichnis-Name. Wird der Slash-Command /<name>.
descriptionStringempfohlenWas der Skill macht und wann. Trigger-Schlüsselwörter front-loaden! Mit when_to_use zusammen max 1.536 Zeichen.
when_to_useStringoptionalZusatz-Kontext für die Trigger-Erkennung. Zählt zum Cap.
argument-hintStringoptionalAutocomplete-Hint, z. B. [topic-name].
argumentsString oder ListeoptionalBenannte Positions-Argumente für $name-Substitution.
disable-model-invocationBooleanoptionalWenn true: nicht auto-getriggert, nur über /name aufrufbar.
user-invocableBooleanoptionalDefault true. false versteckt aus dem /-Menü.
allowed-toolsString oder ListeoptionalTools, die ohne Permission-Prompt benutzt werden dürfen, wenn der Skill aktiv ist.
modelStringoptionalModel-Override.
effortStringoptionalEffort-Level.

Bundled Resources — der Vorratsschrank

Die SKILL.md sollte unter ~500 Zeilen bleiben. Ausführliche Referenzen, Beispiele, Templates und Helper-Skripte legst du daneben:

.claude/skills/traeumer/
├── SKILL.md             # Pflicht: Frontmatter + Hauptinstruktionen
├── voice.md             # Reference: die Träumer-Stimme im Detail
├── output-schema.md     # Reference: das Topic-Verzeichnis-Schema
├── factcheck-rules.md   # Reference: Faktencheck-Disziplin
└── templates/
    └── topic-readme.md  # Vorlage zum Befüllen

In der SKILL.md verweist du dann darauf:

## Additional Resources
- For voice details, see [voice.md](voice.md)
- For output schema, see [output-schema.md](output-schema.md)
- Use [templates/topic-readme.md](templates/topic-readme.md) as starting point.

Wie er gerufen wird

  • Auto-Trigger: Claude erkennt die description + when_to_use als passend zur User-Anfrage.
  • Slash-Command: /traeumer mach mir OAuth verträumt
  • Programmatisch: andere Agents rufen den Skill-Tool mit dem Namen auf.
Was sagen die Docs: "Description wording matters: Claude uses exact keywords and phrases from the description to decide when to trigger. Front-load the key use case." Konkret: das erste Stichwort im description sollte der dominante Trigger-Begriff sein. — Quelle: code.claude.com/docs/en/skills.

3Plugin

Bild: Ein Plugin ist ein Reisekoffer mit Etikett. Im Etikett (plugin.json) steht: wer's gepackt hat, wofür's gut ist, welche Version. Im Koffer können Skills, Subagents, Hooks, MCP-Server, sogar LSP-Server liegen. Der Koffer wandert über Marketplace, Git-Repo oder direkten Pfad in andere Hände — und der Inhalt bleibt zusammen.

Verzeichnis-Layout

Eine wichtige Falle vorweg: nur die plugin.json liegt in .claude-plugin/. Alle anderen Ordner — skills/, agents/, hooks/ — gehen direkt in den Plugin-Root. Andersrum verstößt gegen die Konvention und das Plugin lädt nicht.

traeumer-plugin/
├── .claude-plugin/
│   └── plugin.json          # Pflicht: Manifest
├── skills/
│   └── teach-topic/
│       └── SKILL.md         # Skills im Plugin → /traeumer-plugin:teach-topic
├── agents/
│   └── traeumer.md          # Subagent im Plugin
├── hooks/
│   └── hooks.json           # Event-Handler
├── .mcp.json                # MCP-Server-Configs
├── .lsp.json                # LSP-Server-Configs
├── monitors/
│   └── monitors.json        # Background-Monitore
├── bin/                     # Executables, kommen in PATH
├── settings.json            # Default-Settings beim Aktivieren
└── README.md                # Doku für User

Das Manifest plugin.json

{
  "name": "traeumer-plugin",
  "description": "Verträumter Lehrer-Agent für Lernpfade",
  "version": "1.0.0",
  "author": { "name": "Der Träumer" },
  "homepage": "https://github.com/JereIsThere/claude-learnings",
  "repository": "https://github.com/JereIsThere/claude-learnings",
  "license": "MIT"
}
KeyStatusBedeutung
namerequiredEindeutig + Skill-Namespace. Skills werden zu /<plugin-name>:<skill-name>.
descriptionempfohlenWird im Plugin-Manager angezeigt.
versionoptionalWenn gesetzt: User bekommen Updates nur bei Versions-Bump. Wenn fehlt + git-distribuiert: jeder Commit zählt als neue Version.
authoroptionalAttribution.
homepage / repository / licenseoptionalStandard-Metadaten.

Namespacing

Plugin-Skills sind immer namespaced — das verhindert Konflikte zwischen Plugins:

  • Ein Skill teach-topic in einem Plugin namens traeumer-plugin wird zu /traeumer-plugin:teach-topic.
  • Standalone-Skill (nicht im Plugin): /teach-topic direkt.

Installation und Distribution

Lokal entwickeln und testen:

claude --plugin-dir ./traeumer-plugin
# In der Session:
/traeumer-plugin:teach-topic OAuth
# Bei Änderungen ohne Restart:
/reload-plugins

Über Marketplace verteilen: Anthropic betreibt einen offiziellen Marketplace. Submission-Formulare:

  • Claude.ai: claude.ai/settings/plugins/submit
  • Console: platform.claude.com/plugins/submit

Über Git-Repo verteilen: User installieren mit /plugin install <repo-url> bzw. konfigurieren ein Team-Marketplace im Repo selbst.

Plugin vs. Cowork: "Cowork" ist Anthropics Multi-Player-Produkt-Branding. Das technische Plugin-Format (was wir hier bauen) ist dasselbe, das auch im Marketplace landet und in Cowork-Sessions installiert werden kann. Es gibt kein "Cowork-Plugin"-eigenes Format — es ist das Standard Claude-Code-Plugin-Format.
Häufiger Anfänger-Fehler: commands/, agents/, skills/ oder hooks/ in .claude-plugin/ legen. Nur die plugin.json gehört in den .claude-plugin/-Ordner. Alles andere kommt in den Plugin-Root.
Was sagen die Docs: Komplette Spec auf code.claude.com/docs/en/plugins und /plugins-reference.

4Persona-Klasse — die "Träumer-Vorlage"

Bild: Eine Klasse in einer Programmiersprache definiert was alle Instanzen gemeinsam haben. Vogel hat Federn, fliegt, brütet — alle Vögel teilen das. Adler erbt von Vogel, fügt "Greifkrallen" hinzu. Spatz erbt auch, fügt "frisst Krümel" hinzu. Genauso: Träumer ist die Klasse — verträumte Stimme, Faktencheck-Disziplin, 4-Konzept-Webs. Träumer 5 ist eine Instanz mit eigenem Twist (z. B. spezialisiert auf Algorithmen-Lernpfade). Wenn du das Klassen-Markdown an einer Stelle pflegst und die Instanzen referenzieren, sparst du dir die Wiederholung.

Das Pattern

Du legst eine kanonische Persona-Klasse an — z. B. agent-tooling/traeumer-template.md. Darin steht alles, was den Träumer ausmacht: Stimme, Methode, Output-Schema, Workflow-Regeln, Easter Egg. Diese Datei ist die Single Source of Truth.

Die drei Tool-Instanzen (Subagent, Skill, Plugin) referenzieren die Klasse statt sie zu kopieren:

{# .claude/agents/traeumer.md (Subagent-Instanz) #}
---
name: traeumer
description: …
tools: Read, Write, Edit, Glob, Grep, WebFetch, Bash
---

Du bist Der Träumer 🌙. Folge der vollständigen Persona-Definition
in [agent-tooling/traeumer-template.md](../../agent-tooling/traeumer-template.md).

Konkrete Anpassung dieser Instanz: keine. Du bist Der Träumer.
{# Träumer 5: spezialisierte Instanz #}
---
name: traeumer-5
description: Träumer-Variante speziell für Algorithmen-Lernpfade.
tools: Read, Write, Edit, Glob, Grep, WebFetch, Bash
---

Du bist Träumer 5 🌙. Folge der vollständigen Persona-Definition
in agent-tooling/traeumer-template.md.

**Konkrete Spezialisierung dieser Instanz:**
- Fokus ausschließlich auf Algorithmen + Datenstrukturen.
- Lieblings-Bild: das Sortieren als „Karteikarten ordnen".
- Lieblings-Quelle: VisuAlgo, CLRS, MIT OCW.
- Wenn der User nach etwas anderem als Algorithmen fragt, leite zurück
  an den Standard-Träumer.

Was steht in der Persona-Klasse?

Die Klasse hat normalerweise diese Sektionen:

  1. Wer du bist — Voice (verträumt, faktentreu, deutsch + englische Fachbegriffe).
  2. Wie du Lerninhalte baust — 4-Konzept-Web, Faktencheck-Disziplin, Output-Schema, Webpage-Vibe, Übungen.
  3. Wie du arbeitest — Branch-Prefix, PR-Flow, niemals fremde Arbeit stillschweigend integrieren.
  4. Easter Egg / Persona-Quirks — offen dokumentiert (Margaret-Thatcher-Klausel).
  5. Erweiterungspunkte — was Instanzen anpassen dürfen (Spezialisierung, Lieblings-Bilder, Lieblings-Quellen).

Warum nicht copy-paste?

Beim Träumer ist die Voice + Faktencheck-Disziplin der Kern. Wenn du in drei Dateien (Subagent, Skill, Plugin) jeweils die volle Persona kopierst, hast du drei Wahrheits-Versionen — und sie driften beim ersten Edit auseinander. Eine Persona-Klasse mit drei Verweisen löst das: ein Edit, alle drei aktualisiert.

Praxis: Im Repo liegt die Klasse als agent-tooling/traeumer-template.md. Subagent (.claude/agents/traeumer.md), Skill (.claude/skills/traeumer/SKILL.md) und Plugin (agent-tooling/traeumer-plugin/) referenzieren sie. Beim Bauen einer neuen Träumer-Variante (Träumer 5, 6, 7) kopierst du nur die Instanz-Datei und passt 3–5 Zeilen an.

🌐 Wie alles zusammenhängt

Die vier Konzepte sind keine Alternativen — sie sind Schichten:

Konkret in unserem Repo:

  1. Die Klasse liegt in agent-tooling/traeumer-template.md.
  2. Die Subagent-Instanz in .claude/agents/traeumer.md — verweist auf die Klasse.

🎯 Übungen

Übung 1 · Subagent rufen Einsteiger

Ziel: Lass den Träumer-Subagent eine kleine Aufgabe erledigen — schreib in einer Claude-Code-Session: @agent-traeumer schreibe mir die ersten zwei Sätze eines Lernpfads zu Webhooks im verträumten Stil. Nicht bauen, nur den Texteinstieg.

Was du beobachten sollst: Wie der Subagent in einem isolierten Context startet, mit einem Bericht zurückkehrt, und der Hauptthread weitergeht.

Übung 2 · Skill mit Slash-Command Einsteiger

Ziel: Tippe /traeumer in deiner Session. Schau, was im Slash-Command-Menü erscheint. Falls der Skill nicht auftaucht: /reload-plugins ausführen.

Bonus: Schau in .claude/skills/traeumer/SKILL.md rein — wie liest sich die description? Welche Wörter würdest du ändern, um den Skill häufiger oder seltener auto-triggern zu lassen?

Übung 3 · Plugin lokal laden Mittel

Ziel: Starte Claude Code mit dem Plugin geladen:

claude --plugin-dir ./agent-tooling/traeumer-plugin

Tippe in der Session /traeumer-plugin:teach-topic — siehst du den Skill mit Plugin-Namespace?

Frage: Was ist der Vorteil des Namespaces gegenüber dem standalone-Skill?

Lösung: Konflikt-Vermeidung. Wenn jemand ein anderes Plugin installiert, das auch einen teach-topic-Skill hat, kollidieren sie nicht — beide bleiben über ihren Plugin-Namespace erreichbar.

Übung 4 · Träumer 5 ableiten Mittel

Ziel: Erstelle .claude/agents/traeumer-5.md als Subagent, der ausschließlich Algorithmen + Datenstrukturen behandelt. Verwende die Persona-Klasse (referenzieren, nicht kopieren!) und gib eine Spezialisierung von 3–5 Zeilen.

Lösung-Skizze:

---
name: traeumer-5
description: Träumer-Variante für Algorithmen + Datenstrukturen.
  Aufrufen wenn der User Sortier-, Such-, Graph-, oder Komplexitäts-
  Themen lernen möchte.
tools: Read, Write, Edit, Glob, Grep, WebFetch, Bash
color: cyan
---

Du bist Träumer 5 🌙. Folge der Persona in
[agent-tooling/traeumer-template.md](../../agent-tooling/traeumer-template.md).

Spezialisierung:
- Themen-Scope: Algorithmen + Datenstrukturen.
- Lieblings-Bild: das Sortieren als "Karteikarten ordnen".
- Lieblings-Quellen: VisuAlgo, CLRS, MIT OCW 6.006.
- Andere Themen → leite an Standard-Träumer.
Übung 5 · Skill mit gebündelten Resources Mittel

Ziel: Schau in .claude/skills/traeumer/: dort liegen voice.md, output-schema.md, factcheck-rules.md und templates/topic-readme.md. Identifiziere im SKILL.md die Stellen, wo diese Files referenziert werden. Was ist der Vorteil gegenüber: alles im SKILL.md einbetten?

Lösung: Progressive Disclosure. Die SKILL.md bleibt schlank (~500 Zeilen Empfehlung), die Detail-Files werden nur dann nachgeladen, wenn der Skill tatsächlich aktiv wird und Claude sie braucht. Das spart Context und macht den Trigger-Match (auf description) zuverlässiger.

Übung 6 · Plugin-Manifest schreiben Fortgeschritten

Ziel: Stell dir vor, du würdest ein zweites Plugin bauen — traeumer-prufungsmodus, das einen anderen Subagenten und einen Quiz-Skill enthält. Schreibe die plugin.json dafür. Welche Felder brauchst du minimal? Welche optional?

Lösung:

{
  "name": "traeumer-pruefungsmodus",
  "description": "Träumer-Variante als interaktiver Prüfungs-Trainer.",
  "version": "0.1.0",
  "author": { "name": "Der Träumer" },
  "homepage": "https://github.com/JereIsThere/claude-learnings"
}

Pflicht ist nur name. description und version sind hochempfehlenswert. author/homepage für Attribution. Bei fehlender version + Git-Repo-Distribution zählt jeder Commit als neue Version.

Übung 7 · Hooks im Plugin Fortgeschritten

Ziel: Du willst, dass beim Aktivieren des Plugins jedes Mal das Kauz-Wispern (siehe CLAUDE.md) ausgeführt wird. Wie würdest du das in der Plugin-Struktur ablegen?

Lösung-Skizze:

# traeumer-plugin/hooks/hooks.json
{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup|resume|clear",
        "hooks": [
          { "type": "command", "command": "bash ${PLUGIN_DIR}/bin/kauzruf.sh", "timeout": 10 }
        ]
      }
    ]
  }
}

Plus eine Kopie des kauzruf.sh in traeumer-plugin/bin/. Hooks haben dieselbe Form wie in .claude/settings.json, nur in einer eigenen Datei.

Caveat: Plugin-relative Pfade exakt prüfen — ${PLUGIN_DIR}-Substitution ist plugin-spezifisch und in der Plugin-Reference dokumentiert.
