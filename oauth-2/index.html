Was OAuth ist — und was es nicht ist

OAuth 2.0 ist ein Autorisierungs-Protokoll. Es regelt, wie eine App (der "Client") im Namen eines Nutzers (des "Resource Owner") auf eine API (den "Resource Server") zugreifen darf — ohne dass der Nutzer sein Passwort der App geben muss. Das ist alles. Mehr soll OAuth nicht.

Authentication — also "wer bist du?" — ist nicht der Job von OAuth. Wenn du "Login mit Google" gebaut hast und dachtest, das sei OAuth, hast du in Wahrheit OpenID Connect (OIDC) benutzt — eine Schicht oben drauf. Wir kommen zu OIDC in Konzept 3. Diese Verwechslung ist die Ursache der meisten OAuth-Bugs der letzten 15 Jahre.

Die drei kleinen Worte, die alles erklären

Bild: Die App fragt dich: "Darf ich für dich auf Google Drive lesen?" Du sagst Google: "Ja, das darf sie — aber nur lesen, und nur Drive, nicht Mail." Google gibt der App einen Access Token mit genau diesem eingeschränkten Recht. Die App benutzt den Token bei Drive. Drive prüft den Token. Fertig.

Die vier verbundenen Konzepte

Ohne Rollen & Grants weißt du nicht wer wann was tut. Ohne Authorization Code + PKCE ist dein moderner Flow unsicher. Ohne OIDC hast du keine Authentication. Ohne JWT-Validierung kannst du Tokens nicht überprüfen.

1Rollen & Grant Types

Bild: Vier Schauspieler in einem kleinen Stück. Du (der Resource Owner) sitzt im Zuschauerraum. Eine App (der Client) bittet einen Türsteher (den Authorization Server) um Zutritt zum Tresorraum (dem Resource Server). Du nickst dem Türsteher zu. Der gibt der App einen Pass. Das Stück endet immer gleich — was sich ändert, ist wie die App den Pass holt. Das nennt man "Grant Type".

Die vier Rollen — präzise

  • Resource Owner — der Mensch, dem die Daten gehören.
  • Client — die App, die zugreifen will. Confidential wenn sie ein Secret sicher halten kann (Server-Backend), Public wenn nicht (SPA, Mobile).
  • Authorization Server — die Instanz, die Tokens ausstellt. Hat zwei Endpoints: /authorize (Browser-redirect, Login) und /token (Backend-Call, Token-Tausch).
  • Resource Server — die API, die den Token akzeptiert.

In der Praxis sind Auth-Server und Resource-Server oft beim selben Anbieter (Google, GitHub, Auth0), aber konzeptuell sind sie zwei.

Die Grant Types — ein Entscheidungsbaum

┌─ Hat dein Client ein Backend, in dem ein Secret sicher liegt? │ ├─ Ja (Confidential): Authorization Code Grant + Client-Auth │ └─ Nein (Public, z.B. SPA, Mobile): Authorization Code Grant + PKCE │ ├─ Ist gar kein Mensch beteiligt (Server ↔ Server)? │ └─ Client Credentials Grant │ ├─ Hast du ein Gerät ohne Browser (CLI, Smart-TV, IoT)? │ └─ Device Authorization Grant (RFC 8628) │ └─ Hast du schon einen Access Token, willst nur einen neuen? └─ Refresh Token Grant

Was du heute nicht mehr verwenden solltest

Implicit Grant (response_type=token): Der alte SPA-Flow, bei dem Tokens direkt im URL-Fragment ankommen. Heute durch Authorization Code + PKCE ersetzt.

Resource Owner Password Credentials (ROPC): Die App fragt nach Username + Passwort und reicht sie an den Auth-Server. Wirkt wie ein direkter Login, ist aber ein OAuth-Anti-Pattern — die App sieht das Passwort, was OAuth eigentlich gerade verhindern soll.
Was sagen die Specs:
  • RFC 6749 (OAuth 2.0 Core) definiert beide noch — sie sind in 2012 entstanden, als Browser anders aussahen.
  • RFC 9700 (Security BCP, 2025) sagt zu ROPC wörtlich "MUST NOT be used". Zur Implicit Grant: "SHOULD NOT be used", außer der Server kann Token-Injection im Authorization-Response verhindern.
  • OAuth 2.1 Draft entfernt beide komplett. Wenn du heute neu baust, behandle sie als nicht-existent.

2Authorization Code + PKCE

Bild: Die App schickt dich zum Auth-Server. Du loggst dich dort ein. Der Auth-Server gibt dir einen Code — kein Token! — den du an die App zurückgibst. Die App tauscht den Code (zusammen mit ihrem Geheimnis) am /token-Endpoint gegen den echten Access Token ein. PKCE ist ein zusätzlicher Beweis, den die App schon zu Beginn versprochen hat zu kennen, und den sie beim Token-Tausch einlöst — damit ein Angreifer, der den Code abfängt, ihn nicht einlösen kann.

Der Flow, Schritt für Schritt

App Browser Auth-Server Resource-Server │ │ │ │ │ 1. erzeuge code_verifier (random 43-128 chars) │ code_challenge = BASE64URL(SHA256(code_verifier)) │ │ │ │ 2. redirect zum /authorize-Endpoint mit: │ client_id, redirect_uri, response_type=code, state, code_challenge, code_challenge_method=S256 │ ─────────────────────▶│ │ │ │ ─────────────────────▶│ │ │ ◀──── User loggt sich ein, willigt ein │ │ │ │ │ 3. redirect zur App mit ?code=XYZ&state=... │ │ ◀─────────────────────│ │ ◀─────────────────────│ │ │ │ │ │ 4. POST /token mit: │ grant_type=authorization_code, code=XYZ, │ redirect_uri, client_id, code_verifier │ ─────────────────────────────────────────────▶│ │ │ │ Server prüft: │ │ │ SHA256(code_verifier) == code_challenge? │ │ │ → Ja → access_token + (optional) refresh_token │ ◀─────────────────────────────────────────────│ │ │ │ │ 5. GET /api/resource mit Authorization: Bearer access_token │ ──────────────────────────────────────────────────────────────────────▶│ │ ◀──────────────────────────────────────────────────────────────────────│

Warum PKCE existiert

Auf Mobile (vor PKCE): Eine bösartige App registriert sich für dasselbe Custom-URL-Schema wie deine echte App. Wenn das System den Auth-Code per Redirect ausliefert, fängt sie ihn ab. Ohne PKCE könnte sie damit den Token holen — sie hat ja den Code und brauchte sonst nichts. Mit PKCE: sie hat zwar den Code, aber nicht den code_verifier, der zur ursprünglichen code_challenge passt. Der Token-Tausch scheitert.

PKCE in 3 Zeilen Python

import secrets, hashlib, base64

code_verifier = secrets.token_urlsafe(64)   # ≥43 Zeichen, ≤128
code_challenge = base64.urlsafe_b64encode(
    hashlib.sha256(code_verifier.encode()).digest()
).decode().rstrip('=')              # BASE64URL ohne Padding

# code_challenge geht in /authorize, code_verifier in /token
Was sagen die Specs:
  • RFC 7636 definiert PKCE — ursprünglich (2015) für Native Apps gedacht.
  • RFC 9700 §2.1.1: "Public clients MUST use PKCE." Für Confidential Clients ist es RECOMMENDED, weil es zusätzlich vor Code-Injection schützt. "Authorization servers MUST support PKCE."
  • OAuth 2.1 Draft: PKCE ist "REQUIRED unless the specific requirements of Section 7.5.1 are met" — also de facto Pflicht.
  • RFC 9700 §2.1 zur Redirect-URI: "Authorization servers MUST utilize exact string matching" — keine Wildcards, keine Pfad-Tricks.
Stolperstein: state nicht vergessen! Das ist ein zufälliger Wert, den die App im /authorize-Request mitschickt und im Redirect zurückbekommt. Stimmt der zurückgegebene Wert nicht mit dem gespeicherten überein, ist der Request gefälscht (CSRF). PKCE schützt den Code, state schützt die Redirect-Browser-Session. Du brauchst beide.

3OpenID Connect (OIDC)

Bild: OAuth gibt dir einen Aufkleber, der sagt "diese App darf für Alice das und das tun". OIDC legt einen Personalausweis dazu, der sagt "und übrigens: ich, der Auth-Server, bestätige dir, dass das hier wirklich Alice ist". Der Aufkleber ist der Access Token. Der Personalausweis ist der ID Token.

Der eine Schalter, der OAuth zu OIDC macht

Du machst einen ganz normalen Authorization Code Flow — und schreibst scope=openid in den Request. Mehr nicht. Der Auth-Server gibt dir dann zusätzlich zum Access Token einen ID Token zurück. Das ist OIDC.

GET /authorize?
    response_type=code
    &client_id=...
    &redirect_uri=...
    &scope=openid profile email     ← der "openid" scope schaltet OIDC ein
    &state=...
    &nonce=...                  ← in OIDC empfohlen, in Implicit-Flow REQUIRED
    &code_challenge=...
    &code_challenge_method=S256

ID Token vs Access Token — der zentrale Unterschied

ID Token: für die App selbst, um zu wissen wer der User ist. Immer ein JWT. Validiert die App selbst (Signatur prüfen, Issuer, Audience, Expiry, Nonce).

Access Token: für den Resource-Server, um Zugriff zu bekommen. Format ist nicht festgelegt — kann JWT sein, kann opak sein. Validiert der Resource-Server (lokal als JWT, oder remote per Introspection-Endpoint).

Pflicht-Claims im ID Token

Per OIDC Core 1.0 §2 muss jeder ID Token mindestens enthalten:

  • iss — Issuer Identifier (URL des Auth-Servers).
  • sub — Subject, eindeutige User-ID innerhalb des Issuers. Niemals neu zugewiesen.
  • aud — Audience, muss die client_id deiner App enthalten.
  • exp — Expiry. Nach diesem Zeitpunkt darf der Token nicht akzeptiert werden.
  • iat — Issued At, Zeitstempel der Ausstellung.

Optional: auth_time, nonce, acr (Authentication Context Class), amr (Authentication Methods).

Goldener Validierungs-Fehler: ID Token nur "decoden" und den Inhalt vertrauen. Falsch! Der ID Token ist nur dann eine Aussage des Auth-Servers, wenn du seine Signatur mit dem öffentlichen Schlüssel des Auth-Servers prüfst, iss matched, aud deine client_id enthält, exp in der Zukunft liegt, und (falls geschickt) nonce mit deinem gespeicherten Wert übereinstimmt.

Der UserInfo-Endpoint

Per OIDC Core 1.0 §5.3: ein zusätzlicher Endpoint, an den du den Access Token schickst, und der dir die Claims des Users zurückliefert (Name, E-Mail, …). Praktisch, wenn du Profildaten brauchst, ohne jede einzelne in den ID Token zu pressen.

GET /userinfo HTTP/1.1
Host: example.com
Authorization: Bearer access_token_xyz

→ 200 OK
{
  "sub": "248289761001",
  "name": "Jane Doe",
  "email": "jane@example.com",
  "email_verified": true
}
Was sagen die Specs:
  • OIDC Core 1.0 definiert ID Token, UserInfo, Standard-Claims, Discovery.
  • OIDC Discovery 1.0: jeder OIDC-Provider muss /.well-known/openid-configuration bereitstellen — eine JSON mit allen URLs, Algorithmen, Scopes. Schaff dir die immer als ersten Schritt an.
  • OIDC Core 1.0 §3.1.3.7 listet die genauen ID-Token-Validierungs-Schritte. Lies das einmal komplett.

4JWTs & Token-Validierung

Bild: Ein JWT ist ein Brief mit drei Teilen, die durch Punkte getrennt sind: Umschlag-Aufdruck (Header), Inhalt (Payload), und Wachssiegel (Signature). Wer das Siegel fälschen will, braucht den geheimen Stempel des Absenders. Wer den Brief nur lesen will, braucht nichts — der Inhalt ist nur Base64-kodiert, nicht verschlüsselt.

Aufbau eines JWT

eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiJhbGljZSIsImV4cCI6MTcwMDAwMDAwMH0.signature_bytes
└──── Header ────┘ └────────────── Payload ──────────────┘ └── Signature ──┘

Header  (Base64URL-decoded): {"alg": "RS256"}
Payload (Base64URL-decoded): {"sub": "alice", "exp": 1700000000}
Signature: RSA-SHA256("header.payload", private_key)

Der Payload ist Base64URL, nicht verschlüsselt. Jeder, der den Token sieht, kann ihn lesen. Der Wert eines JWT liegt in der Signatur: nur wer den privaten Schlüssel hat, kann gültige Tokens erzeugen.

Validierung — die ganze Liste

  1. Token in 3 Teile splitten, Header + Payload als JSON parsen.
  2. Algorithmus prüfen: ist alg in deiner Allowlist? Niemals einfach den Wert aus dem Header übernehmen.
  3. Signing Key holen: aus deinem konfigurierten Set, oder über jwks_uri + kid. Niemals Schlüssel-URL aus dem Token lesen.
  4. Signatur prüfen mit dem richtigen Algorithmus. Erst nach erfolgreicher Prüfung gilt der Payload.
  5. Claims prüfen: iss matched? aud enthält dich? exp in der Zukunft? nbf (not before) in der Vergangenheit? nonce matched (falls gesetzt)?

Die drei klassischen Fallen

1. alg=none

Frühe JWT-Bibliotheken akzeptierten Token mit "alg":"none" als gültig — ohne Signatur-Prüfung. Ein Angreifer setzt alg=none, lässt die Signatur weg, und die Library nickt durch.

RFC 8725 §3.1: "The 'none' algorithm should only be used when the JWT is cryptographically protected by other means." Praktisch heißt das: in deiner App-Validation niemals akzeptieren. Whitelist deine erwarteten Algorithmen explizit.

2. RS256 ↔ HS256 Confusion

Dein Auth-Server signiert mit RSA (RS256). Du verifizierst mit dem öffentlichen Schlüssel. Ein Angreifer ändert den Header zu HS256 und benutzt deinen öffentlichen RSA-Schlüssel als HMAC-Geheimnis. Eine schlecht geschriebene Library signiert die HMAC erfolgreich mit dem öffentlichen Schlüssel — und verifiziert auch erfolgreich, weil sie denselben Schlüssel benutzt. Result: Angreifer kann beliebige Tokens fälschen.

RFC 8725 §3.2 / §3.5: "Libraries MUST enable the caller to specify a supported set of algorithms and MUST NOT use any other algorithms." Konkret: konfiguriere deine Library so, dass nur RS256 (oder was auch immer dein Provider benutzt) erlaubt ist. Niemals "decoder, der den Header glaubt".

3. Falscher Schlüssel

Token mit Issuer https://evil.com — du holst den Schlüssel von https://evil.com/.well-known/jwks, weil dein Code blind dem iss-Claim folgt. Der Angreifer hat den Token mit seinem eigenen Schlüssel signiert, alles validiert "korrekt", er ist drin.

RFC 8725 §3.11: "Applications must validate that cryptographic keys belong to the claimed issuer." Sprich: deine Liste der akzeptierten Issuer ist statisch konfiguriert, und nur für die holst du Keys.

Token-Storage im Browser — kurzer Exkurs

Wenn du eine Web-App schreibst und den Token im Browser speicherst:

  • localStorage: per JS lesbar → XSS-Lücke = Token-Diebstahl. Schlecht für sensible Tokens.
  • HttpOnly + Secure + SameSite=Strict Cookie: per JS nicht lesbar, automatisch mitgesendet. Besser, aber CSRF-bedingt nur mit zusätzlichem CSRF-Token oder Same-Origin-Policy einsetzbar.
  • Session-Memory (in JS-Variable, kein Storage): verschwindet bei Reload. Best-Practice für SPA-Access-Tokens — dafür Refresh-Token-Rotation per HttpOnly-Cookie.
Niemand entscheidet das einmal richtig. Speicher-Strategie hängt davon ab: ist es ein Access Token (kurzlebig) oder Refresh Token (langlebig)? Hast du ein Backend? Nutzt du PKCE? Die ehrliche Antwort: lies RFC 9700 §4.4–§4.6 und entscheide für deinen Fall.

📖 Wie liest man die OAuth-Standards?

Bild: Eine RFC ist kein Roman. Du musst nicht von Seite 1 bis 80 lesen. Sie ist ein Lexikon mit klaren Sektionen — wenn du weißt, welche Sektion welche Frage beantwortet, sparst du dir 70 % Lesezeit.

Anatomie einer OAuth-RFC

  • Abstract — 1 Absatz, was das Dokument tut. Immer lesen.
  • Status of This Memo — Standards-Track, Best Current Practice, Informational? Beeinflusst, wie verbindlich die Aussagen sind.
  • §1 Introduction — Motivation. Beim ersten Mal lesen, später überspringbar.
  • §2 Terminology / Conventions — Definitionen. Immer kurz durchfliegen, sonst missverstehst du den Rest.
  • Hauptkapitel — die eigentliche Spec. Hier sind die MUST/SHOULD/MAY-Aussagen (RFC 2119 / 8174 — die Schlüsselwörter sind nicht-zufällig wichtig).
  • Security Considerations — fast immer das nützlichste Kapitel. Explizite Angriffsbeschreibungen und Gegenmaßnahmen.
  • IANA Considerations — überspringbar, außer du registrierst eigene Werte.
  • Appendices — Beispiele, oft sehr hilfreich.

RFC 2119 — die magischen Schlüsselwörter

Wenn du in einer RFC MUST, SHOULD, oder MAY in Großbuchstaben siehst, sind das technische Begriffe:

  • MUST / REQUIRED / SHALL — Pflicht. Wer's nicht macht, ist nicht-konform.
  • MUST NOT / SHALL NOT — Verbot. Wer's macht, ist nicht-konform.
  • SHOULD / RECOMMENDED — sehr empfohlen, Ausnahmen brauchen Begründung.
  • SHOULD NOT / NOT RECOMMENDED — abgeraten, Ausnahmen brauchen Begründung.
  • MAY / OPTIONAL — frei wählbar.

IETF (OAuth) vs OpenID Foundation (OIDC) — zwei Welten

Wichtig zu wissen: OAuth-Standards entstehen in der IETF OAuth Working Group, dokumentiert als RFC. OIDC und Verwandte (CIBA, FAPI) entstehen bei der OpenID Foundation, dokumentiert auf openid.net. Die Prozesse, Versionierung und Naming-Conventions sind anders. Die OAuth-RFCs auf datatracker.ietf.org, OIDC-Specs auf openid.net/specs.

Der Aaron-Parecki-Trick

Aaron Parecki ist Co-Autor mehrerer OAuth-RFCs (PKCE, Device Flow, OAuth 2.1) und der Mensch hinter oauth.net. Wenn dir eine RFC zu trocken ist: such den passenden Talk oder Blog-Post von ihm — die sind exzellent und didaktisch näher an dem, was du dir wünschst. Aber: nutze sie als Einstieg, nicht als Ersatz für die RFC. Die Wahrheit steht im Standard.

🎯 Übungen

Mehrere Übungen sind Lese-Übungen — direkt in den Standards. Das ist Absicht. Diejenigen, die OAuth gut können, haben die RFCs gelesen.

Übung 1 · Rollen-Quiz Einsteiger

Szenario: Du baust eine Mobile-App "ReiseTracker", die deine Google-Maps-Verlaufsdaten lesen soll. Beschrifte:

  1. Wer ist der Resource Owner?
  2. Wer ist der Client? Confidential oder Public?
  3. Wer ist der Authorization Server?
  4. Wer ist der Resource Server?
  5. Welcher Grant Type passt?

Lösung:

  1. Du, der Nutzer.
  2. Die ReiseTracker-App. Public, weil sie auf einem Mobile-Gerät läuft und kein Secret sicher halten kann.
  3. Google Accounts (accounts.google.com).
  4. Google Maps API.
  5. Authorization Code + PKCE (RFC 9700: Public Clients MUST use PKCE).
Übung 2 · PKCE selbst rechnen Einsteiger

Aufgabe: Schreibe in deiner Lieblingssprache eine Funktion pkce_pair(), die ein Tupel (code_verifier, code_challenge) zurückgibt — gemäß RFC 7636: code_verifier ist 43–128 Zeichen Base64URL, code_challenge = BASE64URL(SHA256(code_verifier)) ohne Padding.

Lösung (Python):

import secrets, hashlib, base64

def pkce_pair():
    verifier = secrets.token_urlsafe(64)[:128]
    challenge = base64.urlsafe_b64encode(
        hashlib.sha256(verifier.encode()).digest()
    ).decode().rstrip('=')
    return verifier, challenge

Test: Verifier muss reines Base64URL-Alphabet sein (A-Z a-z 0-9 - _). Challenge muss exakt 43 Zeichen lang sein (256 Bit / 6 Bit-pro-Char ≈ 43, ohne Padding).

Übung 3 · ID Token "decoden" und validieren Mittel

Aufgabe: Öffne jwt.io. Paste einen beliebigen Beispiel-ID-Token (oder generiere einen). Lies Header und Payload. Liste die fünf Pflicht-Claims aus OIDC Core 1.0 §2 (iss, sub, aud, exp, iat). Welcher fehlt im Beispiel? Welche optionalen Claims sind da?

Lösung: Antwort variiert je nach Token. Ziel: du erkennst die Claim-Namen wieder und kannst zwischen Pflicht- und optional-Claims unterscheiden.

Folge-Frage: Würdest du dem Inhalt vertrauen, allein weil iat aktuell aussieht? Nein — ohne Signatur-Prüfung ist der Payload pure Behauptung.

Übung 4 · Lese-Übung: RFC 9700 §2.1 Mittel

Aufgabe: Lies RFC 9700 §2.1 (Protecting Redirect-Based Flows). Beantworte mit eigenen Worten:

  1. Welche Art von String-Matching MUST der Auth-Server für Redirect-URIs benutzen?
  2. Welche zwei Schutzmaßnahmen MUST/SHOULD der Client gegen CSRF anwenden?
  3. Was sagt der BCP zum Thema "open redirectors"?

Lösung: Antworten direkt aus dem Text (Spec-Lesen ist die Übung). Insb. die exakte String-Matching-Regel ist überraschend strikt.

Übung 5 · alg=none demolieren Mittel

Aufgabe: Nimm einen JWT (z. B. von jwt.io). Ändere den Header zu {"alg":"none"}, base64url-encode neu, lasse die Signatur leer. Schreibe in Python einen kaputten Validator, der den Token akzeptiert, und einen korrekten, der ihn ablehnt.

Lösung-Skizze (kaputt):

import base64, json
def validate_bad(token):
    h, p, s = token.split('.')
    header = json.loads(base64.urlsafe_b64decode(h + '='*(4-len(h)%4)))
    if header['alg'] == 'none':
        return json.loads(base64.urlsafe_b64decode(p + '='*(4-len(p)%4)))   # 🚨 vertraut blind
    # … sonst Signatur prüfen …

Korrekt: Algorithmen-Whitelist vor dem Header-Lesen anwenden:

ALLOWED = {'RS256', 'ES256'}
if header['alg'] not in ALLOWED:
    raise ValueError("Algorithmus nicht erlaubt")
Übung 6 · OIDC Discovery erkunden Fortgeschritten

Aufgabe: Hol dir die OIDC-Discovery-Doc von Google: https://accounts.google.com/.well-known/openid-configuration. Beantworte:

  1. Wo ist der authorization_endpoint, der token_endpoint, der userinfo_endpoint?
  2. Welche id_token_signing_alg_values_supported bietet Google?
  3. Welche response_types_supported sind aufgelistet — und welche solltest du heute meiden?
  4. Wo ist der jwks_uri? Hol die JWKs von dort und finde das passende kid für einen ID Token, den du mal in der Praxis bekommen hast.
Übung 7 · Architektur-Entscheidung Fortgeschritten

Szenario: Du baust eine SPA in React + ein Backend in Python (FastAPI). Beide reden mit einem Auth-Provider (Auth0/Keycloak/etc.). Der User soll sich einloggen, dann sollen API-Calls vom Backend an einen dritten Service (z. B. eine eigene Microservice-API) im Namen des Users laufen.

Beantworte mit Begründung:

  1. Welcher Grant Type? Wo läuft PKCE?
  2. Wo wird der Access Token gespeichert: SPA-Memory, HttpOnly-Cookie, localStorage?
  3. Wie kommt das Backend an den Token, um damit den Microservice anzurufen — durchreichen, Token-Exchange, eigener Token?
  4. Welche RFCs zitierst du für deine Entscheidung?

Lösungs-Skizze:

  • (1) Authorization Code + PKCE in der SPA. Public Client.
  • (2) Refresh Token in HttpOnly-Cookie (BFF-Pattern), Access Token in SPA-Memory. RFC 9700 §4.4 zur Rotation.
  • (3) Drei Optionen: durchreichen (einfach, aber Audience-Verletzung wenn der MS einen anderen aud erwartet), Token-Exchange (RFC 8693), oder eigener Service-Token mit Client Credentials (wenn der MS-Call user-unabhängig ist).
  • (4) RFC 6749, RFC 7636, RFC 9700, evtl. RFC 8693 für Token-Exchange.

Es gibt nicht die eine Antwort — die Übung ist, die Trade-offs sauber zu argumentieren.
