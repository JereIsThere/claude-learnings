Was ist Jinja eigentlich?

Jinja (genauer: Jinja2 / Jinja3) ist eine Template-Engine für Python, geschrieben vom Pallets-Team (denselben Leuten, die Flask gebaut haben). Sie ist die Standard-Engine in Flask, im Fundament von Ansible, Salt, FastAPI-Beispielen, der Hugging Face Chat-Templates und vielen mehr.

Eine Template-Engine macht eine sehr konkrete Sache: sie nimmt einen Text mit Platzhaltern und einen Datenbeutel ("Kontext"), und spuckt fertigen Text aus. Klingt simpel — aber sobald mehrere Seiten dasselbe Layout teilen, Daten formatiert werden müssen und Nutzer-Eingaben sicher eingebaut werden sollen, brauchst du Vokabular. Genau das ist heute dran.

Die drei heiligen Klammern

Jinja kennt genau drei Delimiter — alles andere ist normaler Text:

{{ ... }}   # Ausdruck → wird zu Text gerendert
{% ... %}   # Statement → if, for, set, extends, block, …
{# ... #}   # Kommentar → erscheint NICHT im Output

Die vier verbundenen Konzepte

Sie hängen zusammen wie eine Kette: ohne Vererbung wiederholst du dich; ohne Filter & Macros wird die Vererbung schmutzig; ohne klares Verständnis von Kontext & Scope verstehst du nicht, warum Variable X im Block plötzlich verschwunden ist; und ohne Autoescape baust du XSS-Lücken.

1Template Inheritance

Bild: Eine Bauzeichnung für ein Reihenhaus. Die Statik (Wände, Dach, Treppe) wird einmal gezeichnet — das ist deine base.html. Jedes Haus in der Reihe darf nur die markierten Räume umgestalten. Die Markierungen heißen {% block %}.

Der Eltern-Schnittmuster

{# templates/base.html #}
<!doctype html>
<html>
  <head>
    <title>{% block title %}Mein Blog{% endblock %}</title>
  </head>
  <body>
    <header>{% block header %}<h1>Willkommen!</h1>{% endblock %}</header>
    <main>{% block content required %}{% endblock %}</main>
    <footer>© 2026</footer>
  </body>
</html>

Das Kind-Template

{# templates/article.html #}
{% extends "base.html" %}

{% block title %}Artikel — {{ super() }}{% endblock %}

{% block content %}
  <article>
    <h2>{{ post.title }}</h2>
    <p>{{ post.body }}</p>
  </article>
{% endblock %}

Was du gerade gesehen hast

  • {% extends "base.html" %} muss das erste Tag sein. Das Kind kann nur Inhalte in Blöcken ändern — alles außerhalb wird ignoriert.
  • {{ super() }} rendert den Eltern-Inhalt mitten in den Kind-Block. Im Beispiel oben wird der Title zu Artikel — Mein Blog.
  • {% block content required %}: das Kind muss diesen Block überschreiben — sonst Fehler. Ein required-Block darf in der Eltern-Datei nur Whitespace und Kommentare enthalten.
Fakt: Mehrstufige Vererbung ist erlaubt. Du kannst page.html → section.html → base.html erben. Jede Ebene darf weitere Blöcke definieren oder erben.
Stolperstein: Inhalt vor {% extends %} wird stillschweigend verworfen. Wenn dein Kind-Template HTML außerhalb von Blöcken hat, fehlt es im Output — kein Warnung, keine Fehlermeldung.

2Filter & Macros

Bild: Ein Filter ist ein Küchengerät — du wirfst eine Zutat rein, raus kommt eine andere Form (klein gehackt, gepresst, sortiert). Ein Macro ist ein Rezept — du rufst es mit Zutaten auf, und es liefert dir ein fertiges Bauteil zurück. Filter transformieren Daten; Macros produzieren Markup.

Filter — die Pipe-Operator-Familie

{{ name|upper }}                          → ALICE
{{ users|length }}                        → 3
{{ price|round(2) }}                      → 9.99
{{ tags|join(', ') }}                     → "python, flask, jinja"
{{ value|default('—') }}                  → Fallback wenn undefined
{{ posts|sort(attribute='date', reverse=true) }}
{{ user.bio|truncate(80) }}                → schneidet bei 80 Zeichen

Filter lassen sich verketten (Output von links wird Input von rechts):

{{ name|trim|lower|replace(' ', '-') }}     → "max-mustermann"

Eigene Filter (in Flask)

# app.py
@app.template_filter('reverse')
def reverse_filter(s):
    return s[::-1]

Im Template einfach {{ "Hallo"|reverse }} → ollaH. Alternativ ohne Decorator: app.jinja_env.filters['reverse'] = reverse_filter.

Macros — wiederverwendbare Markup-Funktionen

{# _forms.html #}
{% macro input(name, value='', type='text', size=20) -%}
  <input type="{{ type }}"
         name="{{ name }}"
         value="{{ value|e }}"
         size="{{ size }}">
{%- endmacro %}

Aufruf wie eine Funktion:

{{ input('username') }}
{{ input('email', type='email') }}
{{ input('age', type='number', size=4) }}

Die -Zeichen in {%- ... -%} killen umliegenden Whitespace — wichtig wenn Einrückung wichtig ist.

Macros aus anderen Dateien importieren

{% import '_forms.html' as forms %}
{{ forms.input('username') }}

{# Oder gezielt einzelne Macros: #}
{% from '_forms.html' import input, textarea %}

Das {% call %}-Pattern: Macros mit Inhalt

Manchmal willst du einen Macro mit Block-Inhalt aufrufen — wie einen Component-Slot. Dafür gibt's caller():

{% macro card(title) %}
  <div class="card">
    <h3>{{ title }}</h3>
    <div class="body">{{ caller() }}</div>
  </div>
{% endmacro %}

{% call card('Hallo') %}
  <p>Inhalt vom Aufrufer steht hier.</p>
{% endcall %}
Fakt: Innerhalb eines Macros gibt es drei magische Variablen: varargs (extra positionale Args), kwargs (extra Keyword-Args), und caller (der Inhalt aus dem {% call %}-Block, falls einer da war).

3Kontext & Variable Scoping

Bild: Stell dir das Template als eine Bühne vor. Der Kontext ist die Truppe Schauspieler hinter dem Vorhang — Python schickt sie rein. Aber: nicht jeder Schauspieler darf auf jede Bühne. Manche Bühnen (Blocks, Macros) haben Backstage-Türen, die du explizit öffnen musst.

Wie Daten reinkommen

# Pures Jinja2
from jinja2 import Environment, FileSystemLoader
env = Environment(loader=FileSystemLoader('templates'))
template = env.get_template('hello.html')
output = template.render(name='Alice', items=[1, 2, 3])

# In Flask
from flask import render_template
return render_template('hello.html', name='Alice', items=[1, 2, 3])

Lokale Variablen mit {% set %}

{% set total = items|sum %}
<p>Summe: {{ total }}</p>

{# Block-set für Multi-line: #}
{% set greeting %}Hallo, {{ name }}!{% endset %}

Loop-Variablen — die ganze Familie

Innerhalb von {% for %} stellt Jinja diese Variablen bereit:

{% for user in users %}
  {{ loop.index }}     → 1, 2, 3, …  (1-basiert)
  {{ loop.index0 }}    → 0, 1, 2, …  (0-basiert)
  {{ loop.revindex }}  → rückwärts gezählt (1-basiert)
  {{ loop.revindex0 }} → rückwärts (0-basiert)
  {{ loop.first }}     → True bei erstem Element
  {{ loop.last }}      → True bei letztem Element
  {{ loop.length }}    → Anzahl der Items
  {{ loop.previtem }}  → vorheriges Item (oder undefined)
  {{ loop.nextitem }}  → nächstes Item (oder undefined)
  {{ loop.depth }}     → rekursive Tiefe (1-basiert)
  {{ loop.depth0 }}    → rekursive Tiefe (0-basiert)
  {{ loop.cycle('a','b') }}  → zyklisch a, b, a, b, …
  {{ loop.changed(value) }} → True wenn sich value seit letztem Aufruf geändert hat
{% endfor %}

Das große Block-Scoping-Geheimnis

Die größte Stolperfalle in Jinja:

{% for item in items %}
  {% block list_item %}
    {{ item }}   ← FUNKTIONIERT NICHT! `item` ist hier undefined.
  {% endblock %}
{% endfor %}

Warum? Weil ein {% block %} standardmäßig nicht auf Variablen außerhalb des Blocks zugreifen kann. Das ist Absicht: Kind-Templates sollen den Block überschreiben können, ohne plötzlich an äußere Variablen gebunden zu sein. Lösung: das scoped-Schlüsselwort:

{% for item in items %}
  {% block list_item scoped %}
    {{ item }}   ✓ jetzt sichtbar
  {% endblock %}
{% endfor %}

Importieren mit Kontext

Wenn du Macros in eine separate Datei auslagerst, kennen sie standardmäßig den Kontext der aufrufenden Seite nicht (Performance-Optimierung). In Flask sind request, session, g in importierten Templates auch nicht da — es sei denn du sagst:

{% from '_helpers.html' import nav_link with context %}

Flask-Kontext: was du immer hast

Flask injiziert standardmäßig in jedes über render_template() gerenderte Template:

  • config — die Flask-Config (z. B. config['SECRET_KEY'])
  • request — das aktuelle Request-Objekt
  • session — die Session
  • g — der request-gebundene Globals-Speicher
  • url_for() — Routen-Reverse-Lookup
  • get_flashed_messages() — flash messages abrufen

Eigene globale Variablen für jedes Template hinzufügen mit Context Processors:

@app.context_processor
def inject_user():
    return dict(current_user=g.user, year=2026)

Jetzt sind current_user und year in jedem Template verfügbar.

Stolperstein: request, session, g sind nur verfügbar, wenn ein aktiver Request-Context läuft. Beim Rendern aus einem Hintergrund-Job (ohne Request) sind sie weg — und dein Template crasht mit RuntimeError.

4Autoescape & SSTI

Bild: Dein Template ist ein offenes Fenster. Autoescape ist das Fliegengitter: Mücken (<script>-Tags von bösen Nutzern) bleiben draußen. Server-Side Template Injection ist der Albtraum: jemand reißt das ganze Fenster aus dem Rahmen — denn dein Code hat dem Angreifer erlaubt, die Template-Sprache selbst zu schreiben.

Was bedeutet "Escapen"?

Wenn ein Nutzer als Username <script>alert(1)</script> einträgt und du es ungeschützt ins Template schreibst, läuft das Script im Browser jedes Besuchers. Autoescape ersetzt automatisch:

&  →  &amp;
<  →  &lt;
>  →  &gt;
"  →  &quot;
'  →  &#x27;

So wird aus <script>…</script> harmloser Text auf der Seite statt ausgeführter Code.

Default-Verhalten — und der gefährliche Unterschied

Pures Jinja2: Autoescape ist standardmäßig AUS. Du musst es explizit anschalten:
from jinja2 import Environment, FileSystemLoader, select_autoescape

env = Environment(
    loader=FileSystemLoader('templates'),
    autoescape=select_autoescape(['html', 'xml'])
)
Flask: Autoescape ist automatisch AN bei Templates mit Endungen .html, .htm, .xml, .xhtml und .svg, wenn du render_template() benutzt. Bei render_template_string() ist es für alle Strings an.

Die |safe-Falle

Wenn du weißt, dass HTML im Wert sicher ist (z. B. weil eine Markdown-Library ihn produziert hat), kannst du Autoescape gezielt abschalten:

{{ markdown_html|safe }}

Innerhalb eines ganzen Blocks:

{% autoescape false %}
  <p>{{ trusted_html }}</p>
{% endautoescape %}
Goldene Regel: |safe auf irgendetwas aus Nutzer-Eingabe ist eine XSS-Lücke. Punkt. Wenn du es benutzen musst, lass die Quelle vorher durch eine Sanitizer-Library wie bleach laufen.

Server-Side Template Injection (SSTI)

Das ist der richtig große Hammer. SSTI passiert, wenn der Angreifer nicht nur Daten ins Template einbringt — sondern den Template-Quelltext selbst. Beispiel mit dem klassischen Anti-Pattern:

# GEFÄHRLICH — niemals so machen!
@app.route('/hello')
def hello():
    name = request.args.get('name')
    return render_template_string(f'Hallo {name}!')   # ← f-string baut Template-Quelle aus User-Input

Ein Angreifer ruft ?name={{7*7}} auf und sieht Hallo 49!. Das ist die Probe — und ab hier steht die ganze Python-Objektkette offen. Über __class__, __mro__, __subclasses__() kann ein Angreifer Code ausführen, Dateien lesen, in vielen Fällen den ganzen Server übernehmen.

Die einzig richtige Lösung

# SICHER — User-Input nur als Kontext, niemals als Template-Quelle
@app.route('/hello')
def hello():
    name = request.args.get('name')
    return render_template('hello.html', name=name)
    # In hello.html: Hallo {{ name }}!  → bei Autoescape harmlos.

Wenn du wirklich User-Templates ausführen musst

Manchmal will man Power-Usern erlauben, eigene Templates zu schreiben (z. B. für E-Mail-Vorlagen). Dann gibt es jinja2.sandbox.SandboxedEnvironment:

from jinja2.sandbox import SandboxedEnvironment

env = SandboxedEnvironment()
template = env.from_string(user_supplied_template)
output = template.render(name=name)

Die Sandbox blockiert Zugriff auf gefährliche Attribute wie __class__, __mro__ usw. Es gibt auch ImmutableSandboxedEnvironment, das zusätzlich Mutationen an list, set, dict verbietet. Aber: Sandboxes sind in der Geschichte mehrfach umgangen worden — je weniger Funktionalität du Nutzern gibst, desto besser.

Merksatz: Trenne Template (Code, von dir geschrieben) und Kontext (Daten, aus User-Input). Vermische nie beides. Wenn du das Wort "f-string" und "render_template" im selben Atemzug sagst, mach eine Pause und überlege noch mal.

🎯 Übungen — Hände dreckig machen

Setup-Empfehlung: ein Mini-Flask-App in einer einzigen Datei. Installation: pip install Flask.

# app.py — dein Spielplatz
from flask import Flask, render_template, render_template_string, request
app = Flask(__name__)

@app.route('/')
def index():
    return render_template('index.html', name='Welt')

if __name__ == '__main__':
    app.run(debug=True)

Lege dann templates/index.html an und beginne mit Übung 1.

Übung 1 · "Hello name" mit Filter Einsteiger

Ziel: Schreibe ein Template index.html, das {{ name }} anzeigt — aber immer in Großbuchstaben, mit drei Ausrufezeichen am Ende, und falls name leer ist, soll "Anonym" stehen.

Tipp: Du brauchst die Filter upper, default, und Verkettung mit String-Konkatenation oder ~ (Jinja's String-Concat-Operator).

Lösung:

<p>Hallo, {{ (name|default('Anonym', true))|upper }}!!!</p>

Warum true als zweites Argument? Damit default auch bei leeren Strings greift, nicht nur bei undefined.

Übung 2 · Vererbung mit super() Einsteiger

Ziel: Lege base.html mit Title-Block "Mein Blog" an. Lege article.html an, das den Title zu "Artikel-Titel · Mein Blog" erweitert — wobei "Mein Blog" aus dem Eltern-Template kommt, nicht hartkodiert.

Lösung:

{# base.html #}
<title>{% block title %}Mein Blog{% endblock %}</title>

{# article.html #}
{% extends "base.html" %}
{% block title %}{{ post.title }} · {{ super() }}{% endblock %}
Übung 3 · Macro mit caller() Mittel

Ziel: Schreibe ein Macro alert(level), das eine Box mit einer der CSS-Klassen alert-info, alert-warn, alert-error rendert. Der Inhalt der Box soll vom Aufrufer kommen.

Lösung:

{% macro alert(level='info') %}
  <div class="alert alert-{{ level }}">
    {{ caller() }}
  </div>
{% endmacro %}

{% call alert('warn') %}
  <strong>Achtung!</strong> Dein Token läuft bald ab.
{% endcall %}
Übung 4 · Loop-Magie: Trenner zwischen Items Mittel

Ziel: Gegeben tags = ['python', 'web', 'jinja'], gib aus: python, web, jinja. — also Komma zwischen Items, Punkt am Ende.

Lösung A (Loop-Variable):

{% for tag in tags %}{{ tag }}{% if not loop.last %}, {% else %}.{% endif %}{% endfor %}

Lösung B (eleganter, mit join):

{{ tags|join(', ') }}.

Lektion: Loop-Variablen sind mächtig, aber der richtige Filter ist oft kürzer.

Übung 5 · Block-Scoping verstanden? Mittel

Ziel: Folgender Code crasht. Warum? Repariere ihn mit einer einzigen zusätzlichen Code-Vokabel.

{% for product in products %}
  {% block product_card %}
    <h3>{{ product.name }}</h3>
  {% endblock %}
{% endfor %}

Lösung: Das Wort scoped hinter den Block-Namen — Blocks haben standardmäßig keinen Zugriff auf äußere Variablen wie die Loop-Variable product.

{% block product_card scoped %}
Übung 6 · XSS-Detektiv Fortgeschritten

Ziel: Du erbst diesen Flask-Code. Finde zwei Sicherheitslücken — eine offensichtlich, eine subtil.

@app.route('/profile')
def profile():
    bio = request.args.get('bio', '')
    return render_template_string(
        '<h1>Hallo {{ name }}</h1><div>' + bio + '</div>',
        name=request.args.get('name')
    )

Lösung:

  1. SSTI (offensichtlich): bio wird per String-Konkatenation in die Template-Quelle eingebaut. ?bio={{7*7}} würde ausgewertet. Fix: schreib das Template in eine Datei und gib bio als Kontext-Variable.
  2. Subtil: Selbst wenn bio als Kontext käme: render_template_string autoescaped zwar standardmäßig, aber das macht aus bio noch keine "sichere" Variable — wenn jemand später ein |safe dranhängt, ist die Lücke wieder offen. Außerdem: bei render_template_string ist Autoescape immer für alle Strings an, anders als bei render_template, das nach Dateiendung entscheidet — wenn du das vermischst, kann eine Migration zu render_template mit einem .txt-Template plötzlich Autoescape verlieren.
Übung 7 · Eigener Filter Fortgeschritten

Ziel: Schreibe einen Filter moneyize, der eine Zahl zu deutschem Währungsformat macht: 1234.5 → "1.234,50 €".

Lösung:

@app.template_filter('moneyize')
def moneyize(value):
    try:
        n = float(value)
    except (TypeError, ValueError):
        return value
    formatted = f"{n:,.2f}".replace(",", "X").replace(".", ",").replace("X", ".")
    return f"{formatted} €"

Im Template: {{ price|moneyize }}.
